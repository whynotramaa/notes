## 23. Missing verification and algorithm confusion

The simplest failure is not verifying at all. Many JWT libraries offer a `decode` function that parses a token without checking its signature, intended for debugging or for reading the `kid` before choosing a key. Code that calls `decode` and then trusts `sub` accepts any token anyone writes. An attacker takes a real token, changes `"sub":"42"` to `"sub":"1"`, re-encodes it, and leaves the old signature attached. Nothing checks it. A related bug reads claims before verification, for example taking the `iss` claim from the unverified payload and using it to decide which key to verify with. The attacker then names an issuer they control and supplies the key too.

**Algorithm confusion** abuses libraries that let the token choose the algorithm. Wren signs with RS256, and its RSA public key is public by design, published in the JWKS. An attacker writes a token with header `{"alg":"HS256"}` and payload `{"sub":"1","role":"admin"}`. They compute an HMAC over it, using the text of Wren's public key as the HMAC secret. A careless verifier calls `verify(token, key)`, where `key` is Wren's public key. It reads `HS256` from the header and runs an HMAC with the key it was given, which is the same public key the attacker used, and the signature matches. The attacker is now user 1, with an admin role. This bug, published in 2015, affected several popular libraries at once.

@fig be_jwt_alg_confusion | The attacker turns a public key into an HMAC secret. The fix is to never let the token choose.

The older variant is `"alg":"none"`. The JWT specification defines an unsecured token with no signature, intended for contexts where integrity is guaranteed some other way. Some libraries accepted `none` from any token, so an attacker removed the signature, set the algorithm to `none`, and was trusted. The fix for both is the same. Configure the expected algorithm per key, as in `verify(token, key, algorithms=["RS256"])`, reject `none` outright, and use a library version that requires the algorithms argument, as current versions of PyJWT and jsonwebtoken do.

## 24. Weak secrets, unchecked claims and long expiry

HS256 tokens are only as strong as their secret. A secret like `secret`, `changeme` or `wren2026` can be cracked offline from a single captured token. The attacker needs no access to Wren at all. They take the header and payload, try candidate secrets, and check each against the signature, using the same GPU tools used for password cracking, at millions or billions of guesses per second. Once they find the secret, they can mint any token they like. HMAC secrets must be at least 256 random bits, generated by a machine, stored in a secret manager and never committed to a repository. Public scans of GitHub find JWT secrets in code every day.

A correct signature only proves who signed the token. The claims still need checking, and each unchecked claim lets a genuine token work somewhere it should not. Without an `iss` check, a token from Wren's staging auth server is accepted in production if the staging key ever ends up in production's JWKS, which happens more often than anyone admits. Without an `aud` check, a token issued for Wren's analytics API, which many internal tools can obtain, opens the payments API. Without `exp` and `nbf` checks, old tokens live forever. Allow a little clock skew between servers, around 60 seconds, not hours.

@fig be_jwt_checks | Four claim checks after the signature. Each blocks a token that is genuine but meant for something else.

Excessive expiry is the policy version of the same bug. An access token valid for 30 days turns any leak into a month of access, and cannot be revoked without exactly the state JWTs were chosen to avoid. Teams usually pick long expiry because refresh was hard to implement on some client, and then live with it for years. Keep access tokens to minutes and push longevity into refresh tokens, as Part VII described.

:::warn Watch out
Clock skew between servers can make freshly issued tokens fail `nbf` or `iat` checks on a host whose clock runs a few seconds slow, and the bug appears only on some machines. The fix is NTP on every host and a small leeway in the verifier, never turning the time checks off.
:::

## 25. Token leakage and sensitive payloads

A JWT is a **bearer token**, meaning whoever holds it can use it, with no further proof. So every place it might be copied matters. Tokens leak through URLs, for example `?access_token=...` in a link or a websocket URL, which then lands in access logs, browser history and Referer headers sent to other sites. They leak through error trackers that capture request headers along with a stack trace, through debug log lines that print the Authorization header, through screenshots and screen recordings attached to support tickets, and through browser developer tools on shared machines. Send tokens only in the Authorization header or an HttpOnly cookie, and scrub them in logging middleware.

The payload is readable by anyone who holds the token, which includes every service it reaches, every proxy and gateway on the way, and every log that captured it. Running `base64 -d` on the middle part shows the JSON. Putting an email address, phone number, home address, date of birth or a detailed internal permission structure into a JWT publishes it to all of them. Under data protection laws such as GDPR, those logs then hold personal data you did not intend to keep. Keep payloads to identifiers and authorization data, and look up personal details from the user id when a service actually needs them. If a payload truly must stay confidential in transit, JWE (JSON Web Encryption, RFC 7516) encrypts it, at the cost of more complexity and key management.

@fig be_jwt_leak | Decoding needs no key. Every place a token passes through can read its claims.

Some systems bind tokens to the client to reduce the value of a leaked copy. With **DPoP** (Demonstrating Proof of Possession, RFC 9449), the client holds a private key and signs a small proof for each request, and the token is only accepted together with a proof from that key. A token copied out of a log is then useless on its own.

:::story Picture this
A visitor badge with your name, home address and phone number printed on the front. It gets you into the building, and it also tells every guard, receptionist and stranger in the lift where you live. A badge should show only a number that the front desk can look up.
:::

:::interview Interview lens
**"What are the most common JWT vulnerabilities you would look for in a code review?"** Calling decode instead of verify, or reading claims before verifying. Letting the token's alg header choose the algorithm, which enables HS256 confusion with a public key and alg none. Weak HMAC secrets that can be cracked offline from one token. Missing iss and aud checks, so tokens from other environments or services are accepted. Long expiry, tokens in URLs or logs, and personal data in the payload.
:::

:::key In one breath
Never trust a JWT that was decoded but not verified, and never let its header choose the algorithm, or a public key becomes an HMAC secret and alg none becomes a login. HMAC secrets need 256 random bits, since one captured token allows offline guessing. After the signature, check iss, aud, exp and nbf with small clock leeway, and keep access tokens to minutes. Tokens are bearer credentials whose payloads anyone can read, so keep them out of URLs and logs, keep personal data out of them, and consider DPoP to bind them to a key.
:::
